## 2. Event Log Entries — Reference

### TermDD Event ID 56 — Protocol Stream Error / Client Disconnected (Source: TermDD, System log)

Generated by the Terminal Server Driver (TermDD) when the RDP security layer detects an error during the connection handshake and forcibly disconnects the client. With **Network Level Authentication (NLA)** enabled — the default on modern Windows — authentication occurs *before* the full RDP session is established. When credentials fail at the NLA stage, TermDD interprets the failed authentication exchange as a protocol-level error and logs this event alongside the disconnect. This is expected behaviour under NLA, not a sign of a network or TLS problem. The event records the client IP at the point of disconnection.

---

### RdpCoreTS Event ID 140 — Credential Validation Failure (Source: RemoteDesktopServices-RdpCoreTS, System log)

Generated by the RDP Core Transport layer when a connection attempt fails specifically because the supplied username or password is incorrect. This is the RDP subsystem's own record of the authentication failure, complementing the Security log's 4625 entry. It fires at the RDP protocol level rather than the OS authentication level, making it a useful corroborating source when Security audit logging is incomplete or delayed.

---

### RdpCoreTS Event ID 131 — New TCP Connection Accepted (Source: RemoteDesktopServices-RdpCoreTS, System log)

Generated when the RDP server accepts a new inbound TCP connection from a client. This event records the successful **network-layer** connection (TCP handshake complete) but does not imply authentication has succeeded. Its presence at 14:22:07 — followed two seconds later by a successful logon (4624) — confirms the eventual successful session establishment.

---

### Security Event ID 4625 — Account Failed to Log On

Generated for every failed authentication attempt. Logon Type 10 = **RemoteInteractive**, which is the type used exclusively by RDP sessions. Three instances recorded, all from the same source IP and account:

| Time | Account | Failure Reason | Logon Type | Source IP |
|------|---------|---------------|------------|-----------|
| 14:01:04 | FINBRIDGE\bwalker | Unknown username or bad password | 10 (RemoteInteractive) | 10.10.5.44 |
| 14:03:18 | FINBRIDGE\bwalker | Unknown username or bad password | 10 (RemoteInteractive) | 10.10.5.44 |
| 14:05:33 | FINBRIDGE\bwalker | Unknown username or bad password | 10 (RemoteInteractive) | 10.10.5.44 |

**Interval between attempts: ~2 minutes each.** This cadence is consistent with a human user making deliberate retry attempts, not an automated credential-stuffing or brute-force tool (which would operate in milliseconds to seconds).

---

### Security Event ID 4740 — User Account Locked Out

Successful logon from the **same IP address** (10.10.5.44) that generated all previous failures. ## 3. Sequence of Events — Narrative

**14:01:02** — bwalker initiates an RDP connection to the target host from 10.10.5.44. NLA intercepts the credentials before the session is established. The password is incorrect. TermDD disconnects the client (Event 56) and the RDP layer logs the credential failure (Event 140). One second later, the OS security subsystem logs the failed logon (4625, Logon Type 10).

**14:03:18** — bwalker retries the RDP connection approximately two minutes later. Credentials fail again. A second 4625 is recorded.

**14:05:33** — Third retry, same result. A third 4625 is generated.

**14:05:34** — One second after the third failure, Active Directory's Account Lockout Policy triggers. The bwalker account is locked. Any further authentication attempts — RDP or otherwise — will fail with "account locked out" rather than "bad password." (Event 4740).

**14:01 – 14:22** *(gap)* — bwalker is unable to connect. Presumably contacts the helpdesk to request an account unlock. The ~17-minute gap is consistent with a self-reported helpdesk call, wait time, and admin intervention. No unlock event (4767 or 4722) is present in the provided logs — the unlock action may have been logged on the domain controller rather than the target host, or the relevant log window was not captured.

**14:22:07** — The RDP server accepts a new TCP connection from 10.10.5.44 (Event 131). The account has been unlocked.

**14:22:09** — bwalker authenticates successfully via RDP. Logon Type 10 confirmed (Event 4624). Incident resolved.

## 4. Root Cause Assessment

**Root cause: bwalker entered an incorrect password on three consecutive RDP logon attempts from endpoint 10.10.5.44, exhausting the domain Account Lockout Threshold (3 attempts) and triggering an automatic account lockout.**

### Evidence

| Evidence | Significance |
|----------|-------------|
| All three 4625 events carry reason "Unknown username or bad password" — not "Account expired", "Account disabled", or "Restricted hours" | The account was valid and active; only the credential was wrong |
| ~2-minute intervals between attempts | Human-paced retries — not automated attack tooling |
| Source IP 10.10.5.44 is in the RFC1918 10.0.0.0/8 range | Internal network connection — not an external attack |
| Successful 4624 from the same IP 17 minutes later | bwalker is the legitimate owner of this endpoint and knew the correct credentials; the earlier attempts were mistyped, not guessed |
| No change in source IP between failures and success | A single user at a single endpoint, not a distributed attempt |

### What this is not

- **Not a brute-force attack:** Attack tooling would generate hundreds of attempts per minute, not one every two minutes. The 3-attempt count exactly matches the lockout threshold — an attacker would expect this and not stop at 3.
- **Not credential theft / account takeover:** The successful logon from the same IP immediately after unlock rules this out. A threat actor who had stolen credentials would not wait on hold with the helpdesk.
- **Not an RDP vulnerability exploitation:** Event 56 (TermDD protocol error) is standard NLA behaviour on credential failure — it is not indicative of a protocol-level attack such as BlueKeep (CVE-2019-0708).

## 5. Five Why Analysis

**Problem statement:** bwalker was locked out of their RDP session and unable to work remotely for approximately 21 minutes.

---

**Why 1 — Why was the account locked out?**
Because the domain Account Lockout Policy locked the account after 3 consecutive failed RDP logon attempts breached the configured threshold.

---

**Why 2 — Why did bwalker fail authentication 3 times over RDP?**
Because the password entered on each attempt was incorrect. The eventual successful logon from the same machine confirms bwalker knew the correct password — the failures were mistyped credentials, not a forgotten password.

---

**Why 3 — Why did bwalker mistype the password repeatedly over RDP?**
Most likely causes, in order of probability:
- A **recent password change** (within 24–48 hours) that bwalker had not yet memorised or committed to their password manager, leading to muscle-memory errors.
- **Saved/cached credentials** in Windows Credential Manager or the RDP client pointing to the old password, auto-filling the wrong value and causing repeated failures without the user realising it.
- **Keyboard layout or input method** mismatch between the source machine and the RDP client (e.g., Caps Lock, language switching, or special characters behaving differently in the RDP credential prompt).

> *[Action: Confirm with bwalker whether a password change occurred in the 24–48 hours prior. Check Windows Credential Manager on 10.10.5.44 for stale cached RDP credentials.]*

---

**Why 4 — Why did 3 failed attempts result in a lockout?**
Because the domain Account Lockout Threshold is set to 3. This is below Microsoft's recommended baseline of 10 attempts and means a user who mistyped their password three times — a realistic occurrence, particularly with complex passwords over RDP — is automatically locked out with no warning.

> *[Action: Review the Account Lockout Policy GPO. This same threshold was flagged in INC-2024-0315-001 (jsmith lockout). A pattern of lockouts suggests the threshold is operationally too low for the organisation's use case.]*

---

**Why 5 — Why is the threshold set to 3?**
As with the earlier jsmith incident (INC-2024-0315-001), there is no documented rationale for the threshold of 3. It is likely an inherited or arbitrarily conservative value applied without formal security assessment or alignment to operational impact.

> *[Action: Initiate a formal Account Lockout Policy review — this is the second lockout incident on 2024-03-15 alone. The policy threshold, observation window, and self-service unlock capability should all be reviewed against Microsoft Security Baseline and DWP policy standards.]*

## 6. RDP-Specific Security Observations

### NLA Behaviour Confirmed

Event 56 (TermDD) firing alongside Event 140 and 4625 confirms **Network Level Authentication is active** on this RDP host. This is correct and desirable — NLA forces authentication before the RDP session consumes server resources, providing protection against unauthenticated connection exploits and reducing attack surface. No remediation needed here; this is working as intended.

### Source IP Assessment

10.10.5.44 is a private IPv4 address (RFC1918, 10.0.0.0/8). This connection is originating from within the internal network. Key implications:

- The RDP port (3389) does not appear to be exposed to the internet for this host (or the source is VPN-connected). This significantly reduces the security risk profile of the failed logon events.
- If RDP *is* accessible from the internet on this host, that should be remediated — RDP exposure is a top attack vector and is not appropriate without an intermediate gateway (RD Gateway, VPN, or Azure Bastion).

> *[VERIFY: Confirm whether TCP/3389 is exposed externally on the target host. Check firewall rules and network boundary controls.]*

### Cached Credential Risk on RDP Clients

Windows RDP clients save credentials in Credential Manager by default. If bwalker's endpoint (10.10.5.44) has stale credentials cached, every new RDP session will auto-submit the wrong password, rapidly exhausting the lockout threshold before the user can manually enter the correct one. This is a common cause of repeated RDP lockouts after password changes.

```powershell
# Check for cached RDP credentials on the source machine (run as bwalker on 10.10.5.44)
cmdkey /list | Select-String "TERMSRV"

# Remove stale cached credentials for a specific target host
cmdkey /delete:TERMSRV/target-hostname
```

## 9. Preventive Measures

1. **Account Lockout Threshold:** Increase from 3 to the Microsoft-recommended minimum of 10 attempts. Two lockout incidents in a single morning (jsmith at 08:06, bwalker at 14:05) on the same domain indicate the threshold is operationally disruptive. Document the revised value and its rationale.

2. **Credential Manager hygiene:** Train users to clear cached RDP credentials after a password change. Consider enforcing this via logon script or GPO that clears `TERMSRV\*` credentials when a password change is detected.

3. **RD Gateway:** If any RDP access crosses a network boundary, mandate use of an RD Gateway (or equivalent — VPN, Azure Bastion) rather than direct TCP/3389 exposure. This adds an authentication checkpoint and full session logging.

4. **Self-Service Unlock:** Deploying Azure AD SSPR or an on-premises equivalent would allow users to unlock their own accounts without helpdesk involvement, eliminating the 17-minute resolution gap in this and similar incidents.

5. **RDP Alerting:** Configure SIEM alerting on 3 or more 4625 events with Logon Type 10 from the same source IP within a 10-minute window. While this incident was benign, the same event pattern is the opening phase of an RDP brute-force attack. Automated alerting allows security to distinguish legitimate user lockouts from genuine threats quickly.

6. **Failed Logon Reporting:** Produce a weekly report of accounts that hit lockout (4740) — recurring offenders may indicate a systemic cached-credential or process issue rather than user error.
